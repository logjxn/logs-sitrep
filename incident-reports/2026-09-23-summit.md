## Executive Summary

Six malicious samples were analyzed to demonstrate detection and response techniques across multiple levels of the Pyramid of Pain. Detection progressed from easily changed indicators such as file hashes and IP addresses to more attacker-specific behaviors and techniques.

Initial detections relied on known file hashes and network indicators. Subsequent samples demonstrated the limitations of relying solely on these indicators, as attackers could rotate IP addresses, change domains, or modify payloads. Detection was therefore expanded to DNS filtering, behavioral Sigma rules, and MITRE ATT&CK-mapped detections for defense evasion, command-and-control, and data exfiltration techniques.

The exercise resulted in the implementation of multiple containment and detection measures, including application/hash blocking, firewall deny rules, DNS filtering, and Sigma rules targeting attacker-specific behavior.

## Analysis

### Sample 1 - File Hash Detection

`sample1.exe` was identified using a known malicious file hash. The hash was added to a blacklist to prevent execution.

This represents the **hash level of the Pyramid of Pain**. Hashes provide a straightforward method of identifying known malicious files, but they can become ineffective when an attacker modifies the file and produces a new hash.

### Sample 2 - IP-Based Detection

`sample2.exe` demonstrated Metasploit-related activity and established an outbound connection to an unusual external IP address over port `4444`.

An http request was observed targeting:

`hxxp://154.35.10[.]113:4444/uvLk8YI32`

A firewall deny rule was implemented to prevent further egress communication with the identified infrastructure.

This represents the **IP address level of the Pyramid of Pain**. Blocking the infrastructure provides stronger protection against the observed activity, but attackers can replace their infrastructure with another IP address.

### Sample 3 - Domain-Based Detection

`sample3.exe` downloaded `backdoor.exe` from the internet and used the domain:

`hxxp://emudyn.bresonicz[.]info`

Because the attacker could change the underlying IP address while continuing to use domain-based infrastructure, a DNS-level filter was implemented for the identified domain.

This moves detection to the **domain level of the Pyramid of Pain**, making the detection less dependent on a single IP address.

### Sample 4 - Defense Evasion

`sample4.exe` demonstrated behavior beyond simple infrastructure indicators. The sample:

* Disabled Windows Defender monitoring.
* Downloaded executable backdoors from the internet.
* Communicated with `cranes0ft.iniware[.]xyz`.
* Communicated with `102.23.20[.]118`.
* Modified the Windows Defender Real-Time Protection registry configuration.

The registry modification was associated with **MITRE ATT&CK TA0005 - Defense Evasion**.

This activity demonstrates a behavioral detection approach rather than relying exclusively on static indicators such as hashes, IP addresses, or domains.

### Sample 5 - Command and Control Beaconing

Network logs associated with `sample5.exe` showed periodic communications occurring at approximately **30-minute intervals (1,800 seconds)**. The observed packets were consistently **97 bytes** and were sent to the same IP address.

A Sigma rule was created to detect the combination of the observed packet size and 1,800-second interval.

The activity was mapped to **MITRE ATT&CK TA0011 - Command and Control**.

### Sample 6 - Data Exfiltration

`sample6.exe` used an attacker-specific technique where sensitive information was copied to:

`%temp%\exfiltr8.log`

The copied files include directories, local admin groups, system information, network configuration, and active connections being staged.

A Sigma rule was created to detect the specific filename and path relationship.

The activity was mapped to **MITRE ATT&CK TA0010 - Exfiltration**.

This represents a behavioral detection based on the attacker's technique rather than relying on a single hash, IP address, or domain.

## Detection & Blocking

The following containment and detection controls were implemented during the investigation:

1. Blocked the known malicious hash associated with `sample1.exe`.
2. Added a firewall deny rule for the identified malicious IP infrastructure associated with `sample2.exe`.
3. Implemented DNS filtering for the malicious domain associated with `sample3.exe`.
4. Created a Sigma detection for registry modification to HKLM\SOFTWARE\Microsoft\Windows Defender\Real-Time Protection (DisableRealtimeMonitoring set to 1), associated with sample4.exe.
5. Created a Sigma detection for the periodic beaconing behavior, with the time interval and packet size observed in `sample5.exe`.
6. Created a Sigma detection for the attacker-specific file/path behavior observed in `sample6.exe`.

## Lessons Learned

- Hash and IP based detections are quick catches where applicable, but are evaded pretty trivially. Each sample increased the proof that it's easy to alter and evade further.
- Behavioral detection is a much more durable response to malware, as it detects technique rather than small indicators, and this was utilized in the Sigma rules for samples 4, 5 and 6.
- Since the room is a learning environment, the beaconing detection is scoped to the exact size and interval in the sample. Realistically, there will likely be jitter and multiple IPs, so it's something to remember, but the core idea is there.
- Detecting DNS earlier, or only whitelisting allowed domains is a more proactive response to malware. The room focused on analysis after execution.

  condition: selection

level: high
